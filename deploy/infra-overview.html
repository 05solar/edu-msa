모든 설계의 출발점 — 신뢰 모델

이 플랫폼의 사용자는 내부 직원(반신뢰)과 불특정 다수(비신뢰)가 섞여 있다. 그래서 "누가 올렸는가"에 따라 배포 위치와 격리 강도를 자동으로 다르게 적용한다. 판단이 애매하면 항상 더 안전한 쪽(비신뢰)으로 붙이는 fail-closed가 원칙이다.

내부 직원 · 반신뢰

CODER / ADMIN
  • 배포 위치 edu-services 네임스페이스
  • PodSecurity baseline 강제
  • 내부 업무 특성상 사설망 접근 허용

불특정 다수 · 비신뢰

USER / 익명 / 신원 불명
  • 배포 위치 edu-services-public 네임스페이스
  • PodSecurity restricted 강제(비루트·캡드롭·seccomp)
  • 사설망 차단 · 샌드박스 · 유휴 시 0 축소
# 업로더 신뢰도 → 배포 네임스페이스 (fail-closed)
ns(uploader) = if role ∈ { CODER, ADMIN } → edu-services else edu-services-public
# role 이 null·불명·USER 이면 무조건 public (안전한 쪽)

02 · 큰 그림

계층 아키텍처 · edge → platform → tenant → data

외부 요청은 엣지(ingress-nginx)에서 TLS 종료·속도제한·WAF를 통과한 뒤 플랫폼으로 들어온다. 플랫폼(backend)이 배포를 수행하고, 배포된 서비스는 신뢰도에 따라 내부/공개 네임스페이스로 격리된다. 데이터는 CloudNativePG HA, 가시성은 관측성 3축이 담당한다.

03 · 핵심 흐름

배포 파이프라인 · GitHub 레포 → 실행 서비스

백엔드가 레포를 clone해 service.yaml을 파싱·검증하고, 신뢰도로 네임스페이스를 정한 뒤 Kaniko가 도커 소켓 없이 이미지를 빌드해 레지스트리에 올린다. 템플릿을 채워 apply하면 HPA·PDB· NetworkPolicy·PodSecurity가 자동 적용되고, 노드가 이미지를 pull해 파드를 띄우면 서비스가 공개된다.

검증됨 · 실제 GitHub 레포(Go 서비스)를 등록 → 승인 → 자동 배포까지 kind에서 end-to-end 확인.
04 / 15 · 배포 파이프라인
04 · 신뢰성

배포 오케스트레이션 · 작업 큐 + 워커

승인 시 배포를 인메모리 스레드로 바로 돌리면, 서버가 재시작되면 작업이 증발한다. 그래서 배포를 DB 작업 큐(deploy_jobs)에 적재하고, 스케줄러 워커가 FOR UPDATE SKIP LOCKED 행잠금으로 한 건씩만 집어 처리한다. 워커가 여러 개여도 같은 작업을 중복 실행하지 않으며, 실패하면 재시도 후 한도를 넘으면 FAILED로 남는다.

승인 → 큐 적재(202 Accepted) → 워커가 행잠금으로 단일 소비 → 빌드/배포 → DONE 또는 재시도 후 FAILED

05 · 경계 방어

엣지 보안 · TLS · rate-limit · WAF

불특정 다수가 접근하는 외부 경계에서 세 가지를 처리한다. TLS 종료로 암호화를 풀고, 속도 제한으로 폭주를 막고, WAF(ModSecurity + OWASP CRS)로 XSS·SQL 인젝션·경로 탐색 같은 공격 패턴을 차단한다. 정상 요청은 통과(200), 공격은 차단(403), 과도한 요청은 503으로 응답한다.

# WAF 판정  verdict(req) = if match(OWASP-CRS) → 403 elif rate > limit → 503 else 200 · pass

06 · 격리

신뢰 등급별 격리 강도

같은 클러스터 안이라도 내부와 공개 서비스는 담을 다르게 친다. 공개 tier는 restricted 정책, 사설망 egress 차단, 선택적 gVisor 샌드박스, 유휴 시 0 축소까지 더 강한 통제를 받는다.

내부 · edu-services

CODER / ADMIN (반신뢰)
  • PodSecurity baseline 강제(특권·호스트 네임스페이스 금지)
  • Egress 사설망 포함 허용 — 내부 업무 연동
  • 가용성 HPA(CPU 70%) + PDB + 무중단 롤링
  • RBAC edu-deployer가 이 ns에만 배포 권한

공개 · edu-services-public

USER / 익명 / 불명 (비신뢰)
  • PodSecurity restricted(비루트·권한상승금지·캡드롭·seccomp)
  • Egress default-deny + DNS만 — 사설망/데이터 유출 차단
  • 샌드박스 gVisor RuntimeClass(선택)로 커널 격리
  • 비용 KEDA scale-to-zero로 유휴 시 0
CNI는 Calico — kindnet과 달리 NetworkPolicy를 실제로 강제한다(검증: 공개 tier egress 차단 / 내부 tier 허용 대조).

07 · 데이터

데이터 고가용성 · CloudNativePG

PostgreSQL을 오퍼레이터로 3-인스턴스 클러스터로 운영한다. 앱은 항상 edu-db-rw 서비스로만 접속하고, 이 서비스는 현재 primary를 가리킨다. primary가 죽으면 오퍼레이터가 복제본을 자동 승격하고 edu-db-rw가 새 primary로 갱신되어, 앱은 접속 주소를 바꿀 필요가 없다.

검증됨 · primary 파드 삭제 → 복제본(edu-db-1→2) 자동 승격 → 재수렴 확인

유휴 비용 절감 · scale-to-zero

거의 호출되지 않는 서비스가 파드를 계속 점유하면 수만~수십만 규모에서 비용이 선형으로 는다. KEDA HTTP add-on은 유휴 서비스를 0으로 축소하고, 요청이 오면 인터셉터가 요청을 잠시 붙든 채 0→1로 콜드스타트한 뒤 전달한다. 첫 요청만 수 초 지연되고, 이후 다시 유휴가 되면 0으로 돌아간다.

관측성 3축 상관 · metrics · logs · traces

파드에서 나온 메트릭(ServiceMonitor→Prometheus), 로그(Promtail→Loki), 트레이스(OTLP→Tempo)를 Grafana 한 화면에서 본다. 트레이스와 로그는 trace_id로 서로 링크되고, Prometheus 규칙이 임계치를 넘으면 Alertmanager가 알림을 보낸다. 문제 발생 시 지표→로그→트레이스로 한 번에 파고들 수 있다.

10 · 인증서

자동 TLS · cert-manager

인증서를 손으로 만들지 않는다. self-signed로 자체 루트 CA를 한 번 만들고, 그 CA로 서명하는 edu-ca 발급자를 둔다. 서비스 Ingress에 주석 한 줄(cert-manager.io/cluster-issuer)만 붙이면 cert-manager가 인증서를 발급해 시크릿을 자동 생성·갱신한다. 실서버에선 edu-ca를 Let's Encrypt(ACME)로 바꾸면 공인 인증서가 자동 발급된다.

검증됨 · Ingress 주석만으로 ~3초 내 인증서·시크릿 자동 생성(우리 CA 서명, SAN 일치).

레지스트리 pull 경로 · 빌드에서 기동까지

Kaniko가 빌드한 이미지를 노드가 실제로 pull해 파드를 띄우는 마지막 연결이다. 파드(Kaniko)는 레지스트리에 도달 가능한 이름으로 push하고, 노드의 containerd는 localhost:5001 요청을 레지스트리로 해석해 pull한다. 레지스트리는 repo 경로로 저장하므로 push/pull 호스트 이름이 달라도 같은 이미지에 매칭된다.

검증됨 · push한 digest와 노드가 pull한 Image ID digest 동일(221ms) → 서비스 200 응답

부록 · 인증 계층 & 접속

로그인은 auth-service가, 접속은 서브도메인이

계정의 단일 소스를 플랫폼 backend와 분리한 인증 마이크로서비스가 JWT를 발급하고, 각 서비스는 같은 EDU_JWT_SECRET으로 토큰을 자체 검증한다. 배포된 기본 서비스는 포트가 아니라 서브도메인으로 연다.

인증 · auth-service (JWT)

회원가입 · 로그인 · 데모 로그인
  • 자체 DB auth-db · BCrypt 해시 · HS256 JWT
  • Access=응답 본문(메모리) · Refresh=HttpOnly 쿠키
  • backend가 role 클레임으로 RBAC 인가(요청마다 호출 안 함)
  • 교육청 SSO는 이 서비스에 추가 예정 — 토큰 형태 같아 backend 무변경

접속 · 서브도메인 라우팅

http://<slug>.localhost
  • Traefik(:80)이 Host 헤더로 각 컨테이너에 라우팅
  • 배포 시 backend가 /dynamic/<slug>.yml 라우트 기록
  • 같은 eduproxy 네트워크 DNS로 컨테이너명 해소
  • /healthz 준비까지 대기 후 running → 첫 접속 502 방지

기본 내장 서비스는 업무 분야(doc·student·curri·budget·facil·data·civil)별 개인용 단발 도구 7개 — 개인이 접속해 검사·변환·생성·계산·추출을 한 번에 끝내는 도구다.
