edu-msa infrastructure overview

바이브코딩 프로그램을 격리 MSA 서비스로 배포하는 플랫폼

교육청 직원·사용자가 GitHub에 올린 프로그램을 플랫폼이 가져와 안전하게 빌드하고, 업로더 신뢰도에 따라 격리된 네임스페이스의 파드로 배포해 웹에서 바로 쓰게 한다. 아래는 현재 deploy/ 인프라의 구조와 데이터·요청·배포의 전체 흐름을 도면으로 정리한 것이다. 모든 항목은 kind 클러스터에서 실제로 검증하고 서브에이전트로 교차검증했다.

계층 아키텍처

edge → platform → tenant → data

외부에서 들어온 요청은 엣지(ingress-nginx)에서 TLS 종료·속도제한·WAF를 거친 뒤, 플랫폼(edu-platform)의 프론트/백엔드로 가거나 배포된 서비스로 라우팅된다. 배포 서비스는 업로더 신뢰도에 따라 내부(edu-services) 또는 공개(edu-services-public) 네임스페이스로 나뉘어 격리 강도가 달라진다. 데이터는 CloudNativePG HA, 운영 가시성은 관측성 3축이 담당한다.

엣지/경계 플랫폼 코어 내부(반신뢰) 공개(비신뢰) 데이터 관측성
2

배포 파이프라인 · GitHub 레포 → 실행 서비스

backend deploy 도메인

백엔드가 레포를 clone해 service.yaml을 파싱·검증하고, 업로더 신뢰도로 배포 네임스페이스를 결정한다. Kaniko가 호스트 도커 소켓 없이 이미지를 빌드해 레지스트리에 올리고, 템플릿을 채워 kubectl apply하면 HPA·PDB·NetworkPolicy·PodSecurity가 자동 적용된다. 마지막으로 노드가 레지스트리에서 이미지를 pull해 파드를 띄우면 서비스가 공개된다.

# 신뢰도 → 네임스페이스 (fail-closed)
ns(uploader) = if role ∈ {CODER, ADMIN} → edu-services else edu-services-public  // null·불명·USER = public
3

배포 오케스트레이션 · 작업 큐 + 워커

DB 기반 · SKIP LOCKED

승인이 나면 배포를 인메모리 스레드로 바로 돌리지 않고 DB 작업 큐(deploy_jobs)에 적재한다. 스케줄러 워커가 FOR UPDATE SKIP LOCKED 행잠금으로 한 건씩 집어(다중 워커·재시작에도 중복 없음) 빌드·배포를 수행하고, 실패 시 재시도 후 한도 초과면 FAILED로 남긴다.

승인 → 큐 적재(202) → 워커가 행잠금으로 단일 소비 → 빌드/배포 → 성공(DONE) 또는 재시도 후 FAILED
4

요청 흐름 & 신뢰 등급 분리

zero-trust 경계

같은 플랫폼이지만 내부(반신뢰)와 공개(비신뢰) 서비스는 격리 강도가 다르다. 공개 tier는 restricted PodSecurity·사설망 egress 차단·선택적 gVisor·유휴 시 0으로 축소까지 적용해 불특정 다수 노출에 대비한다.

내부 · edu-services

CODER / ADMIN (반신뢰)
  • PodSecurity baseline 강제
  • Egress 사설망 포함 허용(내부 업무)
  • 가용성 HPA + PDB + 무중단 롤링
  • RBAC edu-deployer가 이 ns에만 배포

공개 · edu-services-public

USER / 익명 / 불명 (비신뢰)
  • PodSecurity restricted(비루트·캡드롭·seccomp)
  • Egress 사설망 차단(default-deny + DNS만)
  • 샌드박스 gVisor RuntimeClass(선택)
  • 비용 KEDA scale-to-zero(유휴 0)
# 요청 경로
client ──HTTPS──▶ ingress-nginx [ TLS · rate-limit · WAF ] ──▶ route ∈ { platform, internal, public }
# WAF 판정  verdict(req) = if match(OWASP-CRS) → 403 else pass   // 검증: XSS·SQLi·traversal = 403
5

데이터 고가용성 · CloudNativePG

자동 장애조치

PostgreSQL을 CloudNativePG 오퍼레이터로 3-인스턴스 클러스터로 운영한다. 앱은 항상 edu-db-rw 서비스로 접속하고, 이 서비스는 현재 primary로 라우팅된다. primary 장애 시 오퍼레이터가 복제본을 자동 승격하고 edu-db-rw가 새 primary를 가리키도록 갱신한다(검증: primary 삭제 → 자동 승격 → 재수렴).

6

유휴 비용 절감 · scale-to-zero

KEDA HTTP add-on

거의 호출되지 않는 다수의 서비스가 파드를 계속 점유하면 비용이 선형으로 는다. KEDA HTTP add-on은 유휴 서비스를 0으로 축소하고, 요청이 오면 인터셉터가 요청을 잠시 붙든 채 0→1로 콜드스타트한 뒤 전달한다(검증: 유휴 → replicas 0 → 요청 시 HTTP 200, 2.85s).

7

관측성 3축 상관 · metrics · logs · traces

Grafana 단일 창

파드에서 나온 메트릭(ServiceMonitor→Prometheus), 로그(Promtail→Loki), 트레이스(OTLP→Tempo)를 Grafana 한 곳에서 본다. 트레이스↔로그는 서로 링크되고 (Tempo tracesToLogs / Loki derivedFields), Prometheus 규칙은 Alertmanager로 알림을 보낸다.

멀티테넌트 보안 · 심층 방어

hardening/

한 겹이 뚫려도 다음 겹이 막도록 엣지 → 네임스페이스 → 빌드 → 런타임 → 권한을 층으로 쌓았다. 아래 도면은 요청/코드가 안쪽 서비스에 도달하기까지 통과하는 방어층이다.

바깥에서 안으로: 엣지 방화 → 테넌트 격리 → 안전 빌드 → 런타임 샌드박스 → 최소권한
