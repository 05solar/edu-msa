# MARIADB_PLAN.md · PostgreSQL → MariaDB 전환 계획

서버 배포 DB 를 PostgreSQL 에서 **MariaDB** 로 전환하기 위한 상세 실행 계획이다.
관련 문서: [DEPLOY.md](../operations/DEPLOY.md) · [deploy/INFRA.md](../../deploy/INFRA.md) ·
[GITEA_PLAN.md](GITEA_PLAN.md)

> **배경** — 운영 대상 기관의 요구로 서버 DB 를 MariaDB 로 전환한다. 현행 코드는
> 배포 동시성 제어를 PostgreSQL 전용 기능(부분 유니크 인덱스·SKIP LOCKED)에 의도적으로
> 기대는 설계라, 단순 드라이버 교체가 아니라 **동시성 핵심 장치의 재설계·재검증**이
> 수반된다. 성패는 2단계 실측 검증에 달려 있다.

---

## 사전 결정사항 (작업 시작 전 확정)

| 항목 | 권고 | 근거 |
|---|---|---|
| MariaDB 버전 | **10.6 이상 (11.x LTS 권장)** | `DeployJobRepository` 의 `FOR UPDATE SKIP LOCKED` 가 10.6부터 지원 |
| 문자셋 | **utf8mb4 필수** (서버 기본 + JDBC URL 명시) | 한글 데이터(프로그램 설명 등) |
| 타임존 | 서버·JDBC 모두 **UTC 고정** | MariaDB `DATETIME` 은 타임존 정보가 없음 |
| HA 방식 | 1차 단일 인스턴스 + 백업, HA(mariadb-operator)는 별도 트랙 | CNPG 대체재의 성숙도·범위 관리 |
| 이관 범위 | backend + auth-service DB 2개 (+ Gitea SQLite→MariaDB 겸사) | |

## 1단계 — 애플리케이션 계층 (1.5일)

**의존성·설정**

1. `build.gradle.kts` 2곳(backend·auth-service)에 `mariadb-java-client` 추가.
2. `application.yml` 의 `DB_URL`/`AUTH_DB_URL` 기본값을 `jdbc:mariadb://...` 로 변경
   (env 주입 구조라 변경 범위 작음). JDBC URL 에 타임존(UTC)·utf8mb4 파라미터 명시.
3. Hibernate dialect 는 자동 감지 — 명시 설정 불필요.

**Flyway 마이그레이션 — 벤더 동판 추가**

이미 `locations: classpath:db/migration,classpath:db/vendor/{vendor}` 구조라
`db/vendor/mariadb/` 만 추가하면 되는데, **공통 디렉터리의 V1 이
`bigint generated by default as identity`(표준 identity 문법)를 쓰고 MariaDB 는 이를
지원하지 않는다.** 따라서:

1. identity 문법을 쓰는 공통 파일(V1 등)을 벤더 디렉터리로 이동 — postgresql/h2 는
   현행 유지, mariadb 판은 `bigint auto_increment` 로 재작성.
   엔티티가 `GenerationType.IDENTITY`(9곳)라 auto_increment 와 호환 — **Java 무변경**.
2. V3 mariadb 동판 작성 — plpgsql `DO` 블록·`string_agg(...::text)` 제거(2단계 설계 반영).
3. varchar/text/boolean/current_timestamp 는 그대로 호환(확인 완료).
4. 주의: 벤더 디렉터리는 `db/migration` 밖에 둔다(같은 버전 중복 발견 시 Flyway 기동 거부 —
   application.yml 주석 참조).

**네이티브 쿼리 3건**

| 쿼리 | 판정 | 조치 |
|---|---|---|
| `DeployJobRepository` — `FOR UPDATE SKIP LOCKED` + `now()` | MariaDB 10.6+ 그대로 동작 | 수정 없음, 검증만 |
| `NotificationRepository` — `DELETE ... WHERE id IN (SELECT ... LIMIT)` | **Error 1093** (같은 테이블 서브쿼리 DELETE 금지) | 파생 테이블로 감싸기 `IN (SELECT id FROM (SELECT ...) t)` — PostgreSQL 에서도 동작, 벤더 분기 불필요 |
| `RefreshTokenRepository` — 동일 패턴 | 동일 | 동일 |

**완료 기준** — 두 서비스가 MariaDB 로 기동(Flyway 전 버전 적용 성공, `ddl-auto: validate`
통과), 기존 단위 테스트 전체 통과.

## 2단계 — 동시성 핵심 장치 재설계 (1일) ★ 최우선 리스크

`uq_deploy_jobs_active_program` 부분 유니크 인덱스(`WHERE status IN ('QUEUED','RUNNING')`)가
"프로그램당 활성 배포 작업 1개"의 **최종 심판**인데(코드 주석 명시,
`DeployJobService`·`SlugClaims`) MariaDB 에는 부분 인덱스가 없다.

**대체 설계 — 저장 생성 컬럼 + 유니크 인덱스**

```sql
-- 활성 상태일 때만 program_id, 아니면 NULL 인 저장 생성 컬럼
ALTER TABLE deploy_jobs ADD COLUMN active_program_id BIGINT
  AS (IF(status IN ('QUEUED','RUNNING'), program_id, NULL)) STORED;
CREATE UNIQUE INDEX uq_deploy_jobs_active_program ON deploy_jobs (active_program_id);
```

- 유니크 인덱스는 NULL 중복을 허용하므로 완료/실패 작업은 제약에서 자동으로 빠진다.
- 엔티티에는 매핑하지 않는다(읽기·쓰기 코드 없음 — DB 전용 장치).
  `ddl-auto: validate` 가 미매핑 컬럼을 문제 삼지 않는지 확인.
- 제약 위반은 Spring 예외 변환(`DataIntegrityViolationException`)을 타므로
  기존 처리 로직 무변경 예상 — 실측으로 확인.

**검증(필수 — H2 로는 불가)**

1. 실제 MariaDB 에서 두 워커 동시 INSERT 경쟁 → 한쪽만 성공, 다른 쪽 정상 처리.
2. 상태 전이(QUEUED→RUNNING→SUCCEEDED/FAILED) 후 동일 프로그램 재등록 가능 확인.
3. `SlugClaims` 예약 INSERT(REQUIRES_NEW) 경쟁 경로 동작 확인.

## 3단계 — 인프라 (1.5일)

1. `deploy/docker-compose.yml` — `postgres:16-alpine` 2개(db·auth-db) →
   `mariadb:11` 2개. env(`MARIADB_DATABASE` 등)·healthcheck·volume·JDBC URL,
   utf8mb4 서버 설정(`--character-set-server=utf8mb4`).
2. `deploy/k8s` — `postgres.yaml`·`auth/auth-db.yaml`(단일) → mariadb 매니페스트 교체.
3. **HA 프로필** — `postgres-ha.yaml`·`auth-db-ha.yaml`(CNPG 3-인스턴스 + PgBouncer 풀러)은
   1차 범위에서 **제거·보류**(단일 + 백업). 2차 트랙: mariadb-operator(replication/Galera) +
   MaxScale. read replica 라우팅(`DB_RO_URL` → `edu-db-pooler-ro`)은 미설정 시 라우팅이
   꺼지는 현행 구조 그대로 두면 코드 무변경.
4. `bootstrap.sh` — HA→단일 치환 로직·Secret 이름(`edu-db-app` 등) 정비,
   CNPG 관련 helm 값(podMonitorSelector 등) 제거.
5. 모니터링 — `cnpg_*` 수집 제거 → mysqld_exporter 추가, Grafana 대시보드·알림 룰 수정.
6. 백업 — CNPG 오브젝트 스토리지 백업 → `mariabackup` 크론 + `edu-db-backup-creds` 용도 변경.
7. (겸사) Gitea — `values.yaml` `DB_TYPE: sqlite3` → `mysql` + gitea NetworkPolicy 에
   DB egress 허용 추가. Gitea 는 MariaDB 공식 지원이라 설정만으로 끝.

**완료 기준** — compose·kind 양쪽에서 클린 기동, `prod-preflight` 성격의 점검 항목
(스토리지·Secret) 갱신.

---

## 4단계 — 테스트 전환 (0.5일)

1. 테스트 H2 `MODE=PostgreSQL` → `MODE=MariaDB` (H2 2.x 지원). `db/vendor/h2` 동판이
   mariadb 판과 의미 일치하는지 확인.
2. 2단계 경쟁 경로는 **Testcontainers(MariaDB) 통합 테스트로 격상** — H2 로는
   생성 컬럼+유니크 검증이 안 된다(현행도 partial index 는 PostgreSQL 실측 전제였음).
3. CI 워크플로에 Testcontainers 실행 가능 여부(docker) 확인·반영.

---

## 5단계 — 기존 데이터 이관 (운영 데이터 있는 경우만, 0.5~1일)

1. 서비스 정지 창 확보 → 쓰기 동결.
2. `pg_dump --data-only` 또는 테이블별 CSV export → 변환(boolean `t/f`→`1/0`,
   타임스탬프 UTC 정규화) → MariaDB `LOAD DATA` import.
3. 건수·샘플 대조(테이블별 count + 주요 행 스팟체크) → 시퀀스(auto_increment) 재설정 →
   전환. 롤백 경로: 전환 실패 시 기존 PostgreSQL 재기동(동결 이후 쓰기 없음 전제).

---

## 6단계 — 통합 검증 + 문서 + 릴리스 (1일)

**검증 시나리오(kind, end-to-end)**

1. `bootstrap.sh up` 클린 설치(MariaDB 포함) → 비정상 파드 0.
2. 3역할 로그인 → 프로그램 등록 → 관리자 승인 → real 모드 배포 → 서비스 200.
3. push → webhook → 자동 재배포(작업 큐·SKIP LOCKED 경로 실동작).
4. 알림 생성·페이지네이션·보존 배치(DELETE LIMIT 수정 쿼리) 동작.
5. DB 파드 재시작 후 데이터 유지(PVC), `mariabackup` 백업·복원 리허설 1회.

**릴리스** — 리뷰 PASS → INFRA·PRODUCTION·DEPLOY·SECURITY·VERSIONS 갱신 → 태깅.

## 리스크·운영 유의점

| 리스크 | 대응 |
|---|---|
| 생성 컬럼 유니크가 부분 인덱스와 미묘하게 다르게 동작 | 2단계 실 DB 경쟁 테스트 필수(동시 INSERT 양방향 시나리오) |
| MariaDB `DATETIME` 타임존 없음(PG `timestamp` 와 차이) | 서버·JDBC 타임존 UTC 고정, `Instant` 매핑 왕복 테스트 |
| utf8mb4 인덱스 길이 제한(varchar(255) 유니크) | InnoDB DYNAMIC row format(기본) 3072B 라 안전 — 기동 시 확인 |
| CNPG 대비 HA 성숙도 하락(자동 페일오버·PITR) | 1차 단일 + 백업, HA 는 mariadb-operator 별도 트랙 |
| H2 테스트가 실 DB 차이를 못 잡음 | 핵심 경로 Testcontainers 격상(4단계) |
| SKIP LOCKED 미지원 구버전 배포 | MariaDB 10.6+ 를 전제조건 점검(preflight)에 추가 |

## 구현 결과 (2026-09-14 전환 완료)

### 확정 구성

| 항목 | 값 |
|---|---|
| 버전 | MariaDB **11.4** (최소 요구 10.6 — SKIP LOCKED), InnoDB |
| 문자셋 | utf8mb4 / utf8mb4_unicode_ci (서버 인자로 고정) |
| 타임존 | 서버 TZ=UTC + JDBC `?timezone=UTC` (앱은 기존 Instant/OffsetDateTime 유지) |
| 드라이버 | `org.mariadb.jdbc:mariadb-java-client` + `flyway-mysql` |
| HA | 1차 범위 제외 — 단일 인스턴스 + 일일 백업(계획 §3의 보류안 채택) |

### PostgreSQL ↔ MariaDB 주요 치환

| PostgreSQL | MariaDB 구현 |
|---|---|
| `bigint generated by default as identity` | `bigint auto_increment` (엔티티 IDENTITY 전략 무변경) |
| `timestamp(6) with time zone` | `datetime(6)` (TIMESTAMP 타입은 2038 한계·암묵 DEFAULT 부작용으로 회피) |
| 부분 유니크 `WHERE status IN ('QUEUED','RUNNING')` | **STORED 생성 컬럼** `active_program_id = IF(active, program_id, NULL)` + 유니크 인덱스 (NULL 중복 허용 특성 이용) |
| `DO $$ ... RAISE EXCEPTION` 사전 검사 | `BEGIN NOT ATOMIC ... SIGNAL SQLSTATE '45000'` (Flyway 파싱 검증 완료) |
| `DELETE ... WHERE id IN (SELECT ... LIMIT)` | 파생 테이블 래핑(Error 1093 대응, H2 동일 동작) |
| Flyway `db/vendor/{postgresql,h2}` | `db/vendor/{mariadb,h2}` — 공통 디렉터리에는 V4(완전 호환)만 잔류 |

### 검증 결과 (전부 실측)

- **Testcontainers(MariaDB 11.4)** — backend `MariaDbDeployConcurrencyIT` 8건 전부 통과:
  동시 INSERT 경쟁 승자 정확히 1(패자 DataIntegrityViolationException) · DONE/FAILED 후
  재적재 허용 · active 중 QUEUED/RUNNING 추가 거부 · 프로그램별 독립 · SlugClaims/enqueue
  멱등 · **SKIP LOCKED 2-트랜잭션 잠금 건너뛰기 실측** · 2-워커 12건 경쟁 소진(중복·유실 0) ·
  생성 컬럼 값 전이. auth `MariaDbSchemaMigrationIT` 2건(마이그레이션+validate+시드,
  배치 삭제 쿼리) 통과. Flyway clean install + `ddl-auto: validate` + 시드가 이 과정에서 검증됨.
- **H2 스위트** — MODE=MariaDB 전환 후 backend 92 / auth 24 전부 통과.
- **compose E2E** — clean install(Flyway 5+2 적용) → 3역할 로그인 → 프로그램 등록(201) →
  승인 → 배포 큐(done) → 배포 컨테이너 200 → slug_claims/생성 컬럼 라이브 확인 →
  `mariadb-dump` 백업 → DROP DATABASE → 복원(건수·한글 일치, 앱 무재기동 200) →
  DB 재시작 후 데이터 유지 + 로그인/카탈로그 200.
- 알려진 로컬 개발 참고: Windows + Docker Engine 29 에서 Testcontainers 실행 시
  `~/.docker-java.properties` 에 `api.version=1.44` 필요(Docker 29 가 구형 API 버전을 400 거부).
  CI(Linux)는 불필요. Flyway 가 "MariaDB 11.4 미검증(최신 지원 11.2)" WARN 을 내지만
  전 마이그레이션 정상 적용 확인.
