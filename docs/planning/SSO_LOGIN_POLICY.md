# 로그인 정책 설계 — 대규모·정부기관 전제의 Gitea 연계 SSO

> 전제: 이용자 수십만 명 · 동시접속 수만 명 · 정부기관 보안 정책 준수.
> 목표: **한 번의 로그인으로 플랫폼(포털·API)과 Gitea 를 매끄럽게 오가는** 인증 체계.
> 관련 문서: [GITEA_PLAN.md](GITEA_PLAN.md) §7(2차 SSO), [ARCHITECTURE.md](../architecture/ARCHITECTURE.md)

---

## 1. 결론 요약

| 항목 | 권고 |
| --- | --- |
| 인증 프로토콜 | **OIDC (Authorization Code + PKCE)** — Gitea·플랫폼 공통 |
| 신원 제공자(IdP) | **Keycloak(오픈소스) 중앙 IdP 도입**, 기관 통합인증(교육청 SSO/GPKI)과는 **연합(federation)** |
| 토큰 서명 | 현행 HS256(공유 시크릿) → **RS256/ES256 + JWKS(공개키 검증)** 전환 |
| Gitea 연동 | Gitea 내장 **OAuth2 인증 소스**로 Keycloak 연결 + 자동 가입 + 그룹→팀 매핑 |
| git clone/push 자격 | 웹은 SSO, **git HTTP 는 범위·만료 제한 PAT(개인 액세스 토큰)** — 비밀번호 사용 금지 |
| 다단계 인증(MFA) | 관리자·CODER **의무**(TOTP 기본, WebAuthn/FIDO2 권장), 일반 사용자 선택→단계적 의무화 |
| 계정 수명주기 | IdP 중앙 관리 — 인사 연동 프로비저닝/즉시 차단, 전 구성요소에 동시 반영 |

핵심 논리: 수십만 계정 규모에서는 **비밀번호·계정·MFA·차단을 다루는 곳이 한 곳(IdP)이어야**
안전하고, 플랫폼·Gitea·향후 추가 서비스는 전부 그 IdP 의 **신뢰 당사자(RP)** 로만 동작해야 한다.

## 2. 선택지 비교 — 왜 Keycloak 인가

| 선택지 | 내용 | 대규모·정부기관 관점 평가 |
| --- | --- | --- |
| A. auth-service 를 OIDC Provider 로 확장 | 현행 자체 서비스에 OIDC 발급자 기능을 직접 구현 | **비권고.** 인증 표준(코드 교환·JWKS·세션·동의·로그아웃 전파)을 자체 구현하는 보안 리스크가 크고, 감사·인증(보안성 검토) 대응 부담. 소규모 데모에는 가능하나 이 규모에는 부적합 |
| B. **Keycloak 중앙 IdP** | 검증된 오픈소스 IdP 를 스택에 추가, 플랫폼·Gitea 가 RP 로 위임 | **권고.** OIDC/SAML·MFA·무차별 대입 방어·세션 관리·감사 이벤트·HA 클러스터링이 제품 기능으로 제공. 공공 구축 사례 다수, 오픈소스 원칙(CNR-014)에도 부합 |
| C. 기관 통합인증(교육청 SSO)만 직접 연결 | 각 서비스가 기관 SSO 에 개별 연동 | 단독으로는 비권고 — 외부 사용자(일반인·학부모) 계정을 수용 못 하고, 서비스마다 기관 연동을 반복하게 됨. **Keycloak 뒤에 연합으로 붙이는 구성**이 정석 |

> B + C 조합: Keycloak 이 유일한 로그인 창구가 되고, 교직원은 Keycloak→기관 SSO(브로커링)로,
> 외부 사용자는 Keycloak 자체 계정(또는 간편인증)으로 들어온다. 서비스들은 IdP 가 누구와
> 연합하는지 몰라도 된다 — 지금 auth-service 를 분리해 둔 것과 같은 원리의 확장이다.

## 3. 목표 구조

```
                     ┌────────────────────────────────────────────┐
   교직원 ───────────▶│                                            │◀─── 기관 통합인증(교육청 SSO/GPKI)
   학생·학부모 ──────▶│      Keycloak (중앙 IdP, HA 2+ 노드)        │      · SAML/OIDC 브로커링(연합)
   일반인 ───────────▶│  OIDC 발급 · MFA · 무차별대입 방어 · 감사   │◀─── (선택) 간편인증/휴대폰 본인확인
                     └───────────────┬────────────────────────────┘
                          OIDC (Authorization Code + PKCE)
              ┌──────────────────────┼──────────────────────────┐
              ▼                      ▼                          ▼
     플랫폼 포털/API            Gitea (OAuth2 소스)        향후 추가 서비스
     auth-service = OIDC 위임    자동 가입 + 그룹→팀 매핑     (RP 등록만 하면 SSO)
     (토큰 교환·역할 매핑)        웹 로그인 = SSO
              │                      │
              └── RS256 JWT + JWKS ──┘   각 서비스는 공개키로 자체 검증(무상태 유지)
                                          git clone/push 는 PAT(범위·만료 제한)
```

- **auth-service 는 없어지지 않는다** — OIDC RP(위임)로 전환해 “IdP 토큰 ↔ 플랫폼 역할(USER/CODER/ADMIN)
  매핑, 권한 신청·승인 워크플로” 담당으로 역할이 좁아진다. 발급 토큰 형태를 유지하면
  포털·backend·배포된 웹앱은 **무변경**(현행 설계 의도 그대로).
- 데모 로그인(LOCAL/DEMO)은 시연 환경 전용 플래그로 격리하고 운영 프로파일에서는 비활성한다(현행 지원됨).

## 4. Gitea 쪽 연동 상세

Gitea 는 별도 개발 없이 **내장 기능**으로 아래를 지원한다.

| 항목 | 설정 | 효과 |
| --- | --- | --- |
| OAuth2 인증 소스 | 관리자 → Authentication Sources → OpenID Connect (Keycloak issuer/클라이언트) | 로그인 화면에 "교육청 계정으로 로그인" 버튼 |
| 자동 가입 | `ENABLE_AUTO_REGISTRATION = true` + username/email 클레임 매핑 | 첫 SSO 로그인 시 Gitea 계정 자동 생성(관리자 수동 발급 폐지) |
| 그룹 매핑 | 그룹 클레임 → Gitea 조직/팀 매핑 | IdP 의 부서·역할 그룹이 조직 팀 권한으로 자동 동기화 |
| 로컬 로그인 봉쇄 | 로컬 인증 비활성(또는 관리자 예외만) + `DISABLE_REGISTRATION = true`(현행) | 비밀번호 로그인 경로 제거 — 정책 일원화 |
| 로그아웃 전파 | OIDC RP-Initiated Logout | 포털에서 로그아웃하면 Gitea 세션도 종료 |

**git 명령(clone/push) 자격 증명** — SSO 는 브라우저 흐름이라 git HTTP 에는 쓸 수 없다.

- 사용자: Gitea **개인 액세스 토큰(PAT)** 발급을 표준 절차로 안내 — 범위 최소화(`read/write:repository`),
  만료 90일 이하 의무, 분실 시 즉시 폐기. (현행 배포 봇 `edu-deploy-bot` 토큰 정책과 동일 원칙)
- 플랫폼 파이프라인: 현행 그대로 봇 토큰 + Secret + extraHeader 주입(로그 비노출) 유지.
- SSH 는 현행대로 비활성 유지(포트 22 미개방) — HTTP(S)+PAT 로 단일화가 관제·감사에 유리.

## 5. 토큰·세션 정책 (규모·보안 기준)

| 정책 | 값(권고) | 근거 |
| --- | --- | --- |
| Access Token 수명 | 15~30분 (현행 30분 유지 가능) | 탈취 창 최소화, 무상태 검증과 균형 |
| Refresh Token | 8~24시간 + **회전·재사용 감지**(현행 구현 유지) | 정부기관 세션 정책(장기 세션 금지) |
| 서명 알고리즘 | **RS256/ES256 + JWKS 엔드포인트** | 공유 시크릿(HS256)은 RP 가 늘수록 유출면 확대. 공개키 검증이면 시크릿 배포·회전 문제 소멸, 키 롤오버는 JWKS 로 무중단 |
| 관리자 세션 | 수명 단축(예: 접근 30분/갱신 4시간) + MFA 재검증(step-up) | 고권한 계정 보호 |
| 동시 세션 | 계정당 상한 + 관리 화면에서 원격 종료 | Keycloak 제공 기능 |
| 로그인 방어 | 계정·IP 이중 속도 제한, 실패 잠금(예: 5회/10분), CAPTCHA 단계적 | 수만 동시접속 규모의 크리덴셜 스터핑 대비 |
| MFA | 관리자·CODER 의무(TOTP 기본, WebAuthn 권장), USER 단계적 | 공공 원격접근 다요소 인증 요구 대응 |

**HS256 → JWKS 전환 경로**: auth-service 발급을 RS256 으로 바꾸고 JWKS 공개,
backend·웹앱 검증기를 "JWKS 우선, HS256 폴백"으로 배포 → 전 서비스 전환 확인 후 HS256 폐기.
(검증 로직이 `security/JwtVerifier` 한 곳에 모여 있어 변경 범위가 작다.)

## 6. 수만 동시접속 대비 — 인증 계층 용량

| 구성요소 | 현행(1차) | 대규모 전환 |
| --- | --- | --- |
| Keycloak | (신규) | **2+ 레플리카 클러스터**(Infinispan 캐시) + CNPG PostgreSQL, HPA. 로그인 폭주(출근 30분 기준 수백 TPS)는 [capacity-plan] 산정 방식으로 코어 배정 |
| Gitea DB | SQLite(1단계 임시) | **CNPG PostgreSQL 로 전환 필수** — SQLite 는 동시 쓰기에서 병목·손상 위험 |
| Gitea 캐시/세션 | memory/level(1단계 임시) | **Redis(Valkey)** 로 전환 — 다중 레플리카 전제 조건 |
| Gitea 본체 | 단일 replica + RWO PVC | 세션·캐시 외부화 후 2+ replica(스토리지는 RWX 또는 단일 쓰기 구조 유지 검토) |
| 상시 API 트래픽 | — | 로그인 이후는 **JWT 자체 검증(무상태)** 이라 IdP 부하와 무관 — 현행 구조의 최대 강점, 그대로 유지 |

## 7. 계정 수명주기·감사 (정부기관 요건)

- **프로비저닝**: 인사·학사 데이터와 IdP 연동(배치 또는 SCIM) — 발령·전보 시 그룹 자동 갱신.
- **즉시 차단**: 퇴직·징계 시 IdP 에서 1곳 차단 → 포털·Gitea·전 서비스 동시 차단
  (Refresh 회전 구조 덕에 최대 Access 수명 내 전파). 고위험 시 세션 원격 종료 병행.
- **권한 부여 원칙 유지**: 회원가입(또는 첫 SSO 로그인)은 항상 USER, CODER/ADMIN 상향은
  신청→운영 관리자 승인(현행 워크플로 유지). IdP 그룹은 "후보 자격" 신호로만 쓰고
  최종 부여는 플랫폼 승인 절차를 거치게 해 이중 통제한다.
- **감사로그**: 로그인 성공/실패·MFA·토큰 발급·관리자 행위·PAT 발급/사용을
  중앙 수집(Loki 라벨 표준화, VERSIONS 백로그 A급 "감사로그" 항목과 통합) — 보존 기간은
  기관 지침에 따름(통상 1년 이상). 개인정보 취급 화면 접근 기록 분리 보관.
- **키·시크릿 관리**: IdP 서명키·클라이언트 시크릿·봇 토큰은 Vault/Sealed Secrets 로 보관·주기 회전
  (VERSIONS 백로그 A급 "시크릿 관리"와 동일 트랙).

## 8. 단계적 도입 로드맵

| 단계 | 내용 | 효과 |
| --- | --- | --- |
| 1 | Keycloak HA 설치(스택 편입) + 플랫폼 로그인을 OIDC 위임으로 전환(auth-service = RP) | 로그인 창구 일원화, 기존 토큰 소비 구간 무변경 |
| 2 | Gitea OAuth2 소스 연결 + 자동 가입 + 그룹→팀 매핑, 로컬 로그인 봉쇄 | **포털·Gitea 단일 로그인 완성**(관리자 수동 계정 발급 폐지) |
| 3 | RS256/JWKS 전환 + PAT 정책(범위·만료) 시행 | 공유 시크릿 제거, git 자격 표준화 |
| 4 | 기관 통합인증(교육청 SSO/GPKI) 브로커링 + 인사 연동 프로비저닝 | 교직원 무가입 로그인, 퇴직 즉시 차단 |
| 5 | MFA 의무화(권한 계정→전체), 감사로그·시크릿 금고화 완성 | 정부기관 보안 요건 충족 마감 |
| 6 | Gitea DB(PostgreSQL)·세션(Redis)·레플리카 확장 | 수만 동시접속 용량 확보(§6) |

1~2단계만으로 "한 번 로그인 → 포털+Gitea" 사용자 경험이 완성되고,
3단계부터는 사용자 체감 없이 보안·규모 기반을 올리는 작업이다.

## 9. 현행 대비 변경 범위 요약

| 구성요소 | 변경 |
| --- | --- |
| auth-service | OIDC RP 전환(코드 교환·역할 매핑), RS256 발급 — **가장 큰 변경, 그러나 이 서비스 안에 국한** |
| backend·배포 웹앱 | 검증기 JWKS 지원만 추가(무상태 구조 유지) — 소규모 |
| frontend | 로그인 버튼이 IdP 리다이렉트로 변경 — 소규모 |
| Gitea | 관리자 설정(OAuth2 소스·자동가입·그룹매핑) — **코드 변경 없음** |
| 배포 파이프라인·webhook | 변경 없음(봇 토큰·HMAC 체계 그대로) |
| 신규 도입 | Keycloak(HA), (6단계) Gitea 용 PostgreSQL·Redis |
