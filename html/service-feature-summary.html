01서비스 개요

"레포 하나 = 서비스 하나" — 플랫폼을 관통하는 다섯 가지 핵심 개념

레포 하나 = 서비스 하나

어떤 언어로 만들든(Python·Node·Go·Java·C#…) 레포 루트에 service.yaml과 Dockerfile을 두고, PORT 환경변수로 서버를 열고, /healthz에 200으로 응답하면 새 서비스로 등록·배포됩니다.

무상태 JWT 인증

계정의 단일 소스인 auth-service가 JWT를 발급하고, 각 서비스는 공유 시크릿 (EDU_JWT_SECRET)으로 토큰을 자체 검증합니다. 요청마다 인증 서버를 호출하지 않아 단일 장애점이 없습니다.

최소 권한 원칙

회원가입은 항상 USER로 생성됩니다. CODER·ADMIN 상향은 "신청"만 접수되고, 운영 관리자가 승인해야 부여됩니다. 자가 가입·신청만으로는 권한이 오르지 않습니다.

신뢰도별 격리

내부 직원의 서비스는 edu-services(baseline), 불특정 사용자의 서비스는 edu-services-public(restricted) 네임스페이스로 자동 분리되며, 판단이 애매하면 더 엄격한 쪽으로 배치됩니다(fail-closed).

서브도메인 접속

배포된 서비스는 포트 번호가 아니라 http://<slug>.localhost (로컬 Traefik) 또는 실서버 ingress-nginx 서브도메인으로 열립니다.

원커맨드 배포

./deploy/bootstrap.sh up 하나로 클러스터 준비부터 이미지 빌드, 코어·운영 스택 배포까지 완료됩니다. kind 로컬과 실서버(edu-poc.headit.kr)를 겸용합니다.

03인증 · 권한 체계

auth-service가 발급, 각 서비스가 자체 검증

역할 3등급

역할대상할 수 있는 것부여 방식
USER외부 사용자 탐색·상세·바로 사용·즐겨찾기·알림·의견 작성, 상향 권한 신청회원가입 기본값
CODER내부 직원 (바이브 코더) USER 전체 + 프로그램 등록, 레포 규격 자가 검증, 본인 프로그램 재배포신청 → 관리자 승인
ADMIN운영 관리자 CODER 전체 + 등록 승인/반려, 배포 실행, 공개 중지/재개, 권한 신청 처리, 사용자·카테고리 관리신청 → 관리자 승인

권한 상향 신청 흐름

가입 시 requestRole
또는 마이페이지에서 신청→ 승인 대기
계정은 USER 유지→ 관리자 승인 / 반려→ 승인 시 권한 상향
  • 신청자는 승인 전 언제든 신청을 취소할 수 있습니다 (DELETE /api/auth/role-request).
  • 관리자는 신청 목록에서 이름·부서·현재/신청 권한·사유를 보고 승인 또는 반려합니다.

토큰 · 세션 보안

  • Access Token (HS256, 기본 30분) — 응답 본문으로 받아 메모리에만 보관(XSS 대비 localStorage 미사용). 만료 60초 전 자동 재발급.
  • Refresh Token (기본 14일) — HttpOnly 쿠키 edu_refresh. DB에는 원문 대신 SHA-256 해시로 저장.
  • 토큰 회전 + 탈취 감지 — 갱신할 때마다 기존 토큰을 폐기하고 재발급하며, 폐기된 토큰의 재사용이 감지되면 해당 계정의 전체 세션을 무효화합니다.
  • 시크릿 EDU_JWT_SECRET은 32바이트 미만이거나 미설정이면 서비스가 기동을 거부합니다(의도된 안전장치).

데모 로그인 (시연용)

로그인 화면의 "데모로 시작하기"로 비밀번호 없이 진입하지만, 발급되는 토큰은 일반 로그인과 동일하여 등록·승인·배포 등 실제 API를 그대로 사용할 수 있습니다. 사이드바의 "시연용 권한 전환"은 화면만 바꾸는 것이 아니라 해당 역할의 데모 계정으로 토큰을 재발급받아 서버 권한과 화면이 어긋나지 않습니다. 데모 세션은 1일로 짧게 제한되며 설정으로 비활성화할 수 있습니다.

04화면별 기능 (프론트엔드)

인증 전 4개 화면 + 로그인 후 8개 화면 · 공통 셸

인증 전 화면

로그인

  • 아이디/비밀번호 로그인(클라이언트 검증 포함)
  • 시연용 구획의 "데모로 시작하기" 버튼
  • 회원가입·아이디 찾기·비밀번호 찾기 이동 링크
  • 좌측 패널에 로그인 없이 열람 가능한 직원용·관리자용 안내서 링크

회원가입

  • 아이디·이메일 중복확인 버튼, 비밀번호 복잡도 실시간 체크리스트
  • 권한 신청(선택) — 바이브 코더/운영 관리자 + 사유 300자
  • 계정은 항상 USER로 생성, 상향은 승인 대기로만 저장
  • 이메일/휴대폰 본인 확인은 SMTP·SMS 연동 후 활성화 예정

아이디 찾기 · 비밀번호 찾기

  • 2단계 스텝 UI(본인 확인 → 결과/재설정 안내)
  • 이름·이메일·아이디 입력값 검증까지 동작
  • 실제 조회·재설정 메일 발송은 SMTP 연동 후 완성

공통 셸 (사이드바 · 상단바)

  • 역할별 메뉴 필터링, 알림·검토 대기 수 배지, 접기/펼치기
  • 데모 진입 시에만 "시연용 권한 전환" 노출
  • 글자 크기 8단계 조절, 라이트/다크 테마 토글(모두 저장됨)
  • 상단 검색창(엔터 시 탐색 목록으로), 토스트·모달 시스템

로그인 후 주요 화면

홈 전체

  • 업무 설명 검색 히어로 + 추천 검색어 칩
  • 7개 업무 분야 바로가기(분야별 프로그램 수 표시)
  • 즐겨찾기(최대 5개), 조회수 기준 인기 순위 8개, 최근 업데이트 4개
  • 하단 프로그램 등록 유도 배너

프로그램 탐색 전체

  • 필터: 검색어 · 업무 분야 · 기능 유형(복수) · 기술 태그(복수) · 공개 범위

  • 공개 범위 규칙: 전체 공개이거나 같은 부서일 때만 노출

AI로 프로그램 찾기 전체

  • 챗봇 형태 — 업무를 문장으로 설명하면 상위 3개 추천
  • 공개 프로그램의 이름·요약·설명·태그를 키워드 매칭(데모 로직, 외부 API 미사용)

내 프로그램 / 마이페이지 전체

  • 내 권한 패널 — 현재 권한 확인, 상향 신청·승인 대기·신청 취소

운영 관리자 ADMIN

  • 검토 대기: 승인 / 배포(파이프라인 로그·K8s 매니페스트 확인) / 반려(사유 입력, 등록자 알림)
  • 권한 요청: 상향 신청 승인·반려
  • 전체 프로그램: 공개 중지·재공개·승인
  • 처리 이력: 승인/반려/중지/재개 로그
  • 운영 현황: 통계 카드, 분야별 등록 현황 그래프, 사용자 권한 직접 변경
  • 카테고리 관리: 분야별 현황(편집은 시연용)

바로 사용 모달 전체

  • 제공 방식 목록(웹/다운로드/설치/Gitea/매뉴얼) 표시
  • 배포 완료(running) 상태면 "웹에서 바로 사용"을 실제 서비스 URL로 연결
API 모드 / 목업 모드 — 기본은 백엔드 연동 모드(VITE_USE_API=true)이며, false로 두면 목업 데이터만으로 도는 오프라인 데모가 됩니다. 단, 인증(auth-service)은 항상 실제 서버를 호출하고, 레포 검증·배포·재배포는 API 모드 전용입니다.

05프로그램 라이프사이클

등록 → 검토 → 배포 → 공개 상태 머신

draft→ 제출 → pending→ 승인 + 배포 성공 → public
pending→ 반려 → rejected public→ 중지 ⇄ 재개 → stopped
  • 등록 — CODER 이상이 등록 요청하면 pending으로 저장되고 관리자에게 제출 알림이 갑니다.
  • 승인 시 자동 배포 — 승인하면 즉시 공개하지 않고 배포 작업 큐에 적재되며, 배포가 성공해야 자동으로 공개(public) 전환됩니다(설정으로 자동 배포 끄면 즉시 공개).
  • 반려·중지 — 사유가 저장되어 등록자 화면(내 프로그램·상세)에 그대로 표시되고 알림이 발송됩니다.
  • 재배포 — 소유자 본인만(관리자는 전체) 공개 상태의 프로그램에 대해 실행할 수 있고, 레포 주소는 서버에 저장된 값만 사용해 임의 주입을 차단합니다. 새 버전 번호는 이력(history)에 기록됩니다.

배포 오케스트레이션 (작업 큐 + 워커)

  • 배포 요청은 즉시 실행되지 않고 DB 작업 큐(deploy_jobs)에 적재된 뒤 워커가 3초 주기로 처리합니다.
  • FOR UPDATE SKIP LOCKED 행 잠금으로 백엔드가 여러 인스턴스여도 같은 작업을 중복 처리하지 않습니다.
  • 실패 시 최대 2회까지 자동 재시도하고, 초과하면 실패로 확정되어 실패 원인이 프로그램 상세에 표시됩니다.
  • 배포 진행 상태: PENDING → VALIDATING → BUILDING → DEPLOYING → RUNNING / FAILED. docker 모드는 조회 시 컨테이너 생존까지 확인합니다.

레포 주소 형식

  • https://github.com/… — 실제 GitHub 레포 (얕은 clone, 브랜치 지정 가능)
  • local://examples/<slug> — 플랫폼에 동봉된 기본 서비스 7종
  • sample://<name> — 오프라인 검증 전용 번들

07표준 서비스 규격 (바이브 코더 계약)

이 5가지만 지키면 언어는 자유

규칙 1 — 레포 하나 = 서비스 하나

GitHub 레포지토리 하나가 배포 단위입니다.

규칙 2 — service.yaml

레포 루트에 서비스 설명서를 둡니다. name·slug·category·port가 필수입니다.

규칙 3 — Dockerfile

레포 루트에 실행 방법을 둡니다. 비루트 실행·멀티스테이지 빌드 권장.

규칙 4 — PORT 환경변수

플랫폼이 주입하는 PORT로 웹 서버를 엽니다. 하드코딩 금지.

규칙 5 — 헬스 체크

GET /healthz가 200으로 응답해야 배포가 완료됩니다(시작 30초 내 권장).

공통 — 오류 · 로그

오류는 {"error":{"code","message"}} JSON으로, 로그는 stdout/stderr로. 무상태 권장.

service.yaml 스키마

name: string          # 필수. 표시 이름
slug: string          # 필수. ^[a-z][a-z0-9-]{1,38}$ (URL·K8s 식별자, 전역 유일)
category: enum        # 필수. doc | student | curri | budget | facil | data | civil
port: int             # 필수. 1024–65535
purposes: [enum]      # 선택. auto | gen | verify | analyze | summary | search | dash
tech: [string]        # 선택. 자유 표기
summary: string       # 선택. 한 줄 소개 (120자 이내)
health: string        # 선택. 기본 "/healthz"
resources:            # 선택. 기본 cpu 250m / memory 256Mi / gpu 0
  gpu: 0              # 1 이상이면 nvidia.com/gpu 요청 (0–8, GPU Operator 필요)

등록 시 플랫폼이 7가지 정적 검증(YAML 파싱, 필수값·형식, slug 정규식·유일성, category enum, Dockerfile 존재, 레포 접근성, 헬스 경로)을 자동 수행하고 실패 항목을 반려 사유로 표시합니다. 시크릿은 service.yaml에 넣지 않으며, 개인정보는 레포에 커밋하지 않습니다.

10인프라 · 보안

멀티테넌트 하드닝 + 운영 스택 (P0–P3 실구현 완료)

격리 · 하드닝 적용됨

  • 신뢰등급 네임스페이스 분리 + PodSecurity (baseline / restricted)
  • NetworkPolicy: default-deny + DNS·Ingress만 허용, 사설망·메타데이터 차단
  • 서비스 컨테이너: 비루트, 권한 상승 금지, capabilities 전부 drop, seccomp
  • Kaniko 인클러스터 빌드 — docker.sock 노출 없는 안전 빌드
  • ResourceQuota · LimitRange, gVisor RuntimeClass 준비

가용성 · 확장 적용됨

  • 오토스케일: HPA + PDB (무중단 롤링 업데이트)
  • DB HA: CloudNativePG 3-인스턴스
  • 유휴 서비스 scale-to-zero: KEDA HTTP add-on
  • 배포 큐 + 워커로 다중 인스턴스 안전 처리

관측성 · 엣지 적용됨

  • 메트릭: Prometheus + Grafana, 로그: Loki + Promtail, 트레이스: Tempo
  • 게이트웨이: ingress-nginx + WAF(ModSecurity / OWASP CRS)
  • 자동 TLS: cert-manager, 알림: Alertmanager
  • 사내 컨테이너 레지스트리 pull 경로

남은 과제 프로덕션 전

  • EDU_JWT_SECRET의 Vault / Sealed Secrets 이관·회전 (최우선)
  • 감사 로그 · 실제 OTel 앱 계측
  • gVisor/Kata 샌드박스 노드 실설치
실행 방법 요약 — 로컬은 docker compose -f deploy/docker-compose.yml up (postgres·auth-db·auth-service·traefik·backend) + npm run dev(프론트, :5173). K8s는 ./deploy/bootstrap.sh up 하나로 kind 로컬과 실서버를 겸용하며, 실서버(edu-poc.headit.kr)는 make prod-* 타겟으로 배포합니다. 플랫폼 코어는 CPU 전용이고 GPU는 테넌트 서비스가 resources.gpu로 요청할 때만 사용됩니다.
