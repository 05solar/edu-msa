01 · 큰 그림

시스템 한눈에 — 무엇이 어디에 있나

사용자는 플랫폼 UI로 들어와 로그인하고 프로그램을 찾아 쓴다. UI 뒤에는 인증 전담 auth-service, 플랫폼 API backend, 그리고 배포된 서비스로 연결하는 리버스 프록시 Traefik가 있다. 배포된 개인용 도구들은 서브도메인으로 바로 열린다.

인증(auth-service) 플랫폼(frontend·backend) 라우팅(Traefik) 배포된 서비스
02 · 구성요소

각 구성요소는 무슨 역할을 하나

시스템은 역할이 분명한 몇 개의 서비스로 나뉜다. 인증은 인증만, 플랫폼 API는 카탈로그·배포만 맡아 관심사가 분리되어 있고, 데이터도 각자의 DB로 나뉜다.

플랫폼 UI

Frontend

React+Vite. 로그인·카탈로그·등록·마이페이지·운영 관리자 화면. 토큰을 붙여 API 호출, 로컬은 /api·/api/auth를 각 서버로 프록시.

인증

auth-service

계정의 단일 소스. 회원가입·로그인·데모로그인, JWT(Access+Refresh) 발급/회전. 자체 DB(auth-db) 사용.

플랫폼 API

backend

프로그램 카탈로그·등록·검토·배포 파이프라인. 요청의 JWT를 스스로 검증해 역할(RBAC)로 인가.

데이터

auth-db

계정·비밀번호 해시(BCrypt)·권한 신청 상태. 플랫폼 DB와 분리해 계정 정보를 한 곳에 둔다.

데이터

platform-db

프로그램·배포 기록·알림·처리 이력. 서비스 소스는 담지 않고 메타데이터만.

라우팅

Traefik

리버스 프록시. <slug>.localhost Host로 각 배포 컨테이너에 연결. backend가 라우트 파일을 써 넣으면 감시해 반영.

배포 파이프라인

deploy(백엔드 내부)

레포 수집→규격 검증→이미지 빌드→컨테이너/파드 기동→헬스 대기→공개. simulate·docker·real 모드.

배포 결과

examples · 7 서비스

기본 내장 개인용 단발 도구 7종(카테고리별 1개). 각 폴더가 service.yaml·Dockerfile을 갖춘 배포 가능한 레포.

실행 기반

Kubernetes

실서버 오케스트레이션. 신뢰등급 네임스페이스·격리·오토스케일·관측성. 로컬은 docker-compose로 대체.

03 · 설계 전제

신뢰 모델과 역할(권한)

사용자는 내부 직원과 불특정 다수가 섞여 있다. 그래서 회원가입은 항상 최소 권한으로 만들고, 상향 권한은 신청 → 운영 관리자 승인으로만 부여한다. 판단이 애매하면 항상 더 안전한 쪽으로 붙이는 fail-closed가 원칙이다.

역할 3단계

JWT role 클레임으로 서버가 판단
  • USER · 외부 사용자 — 열람·사용. 회원가입 기본값
  • CODER · 내부 직원 — 프로그램 등록·레포 규격 검증
  • ADMIN · 운영 관리자 — 검토·승인·배포·권한 부여

권한 상향은 신청+승인

자가 가입/신청만으로는 오르지 않음
  • 가입 시 requestRole 또는 마이페이지에서 신청
  • 계정은 그대로 USER, "승인 대기"만 보관
  • 운영 관리자가 승인 시 실제 role 반영, 반려 시 USER 유지
실서버 배포 격리도 같은 신뢰 모델을 따른다 — 내부 직원 서비스는 edu-services(baseline), 불특정 다수 서비스는 edu-services-public(restricted) 네임스페이스로 자동 배치(§08).
04 · 흐름 ① 인증

로그인은 auth-service가, 검증은 각 서비스가

로그인하면 auth-service가 JWT를 발급한다. 이후 플랫폼 API는 매 요청마다 auth-service를 부르지 않고, backend가 같은 서명키로 토큰을 스스로 검증한다. 아래 점선의 흐르는 점이 토큰이 이동하는 방향이다.

인증 발급 흐름 토큰 사용(검증) 흐름 흐르는 점 = 데이터 이동 방향
데모 로그인도 같은 형태의 토큰을 받으므로 진입 후 실제 API를 그대로 쓴다. 교육청 SSO가 추가돼도 토큰 형태가 같아 backend·각 서비스는 바뀌지 않는다.
05 · 흐름 ② 등록에서 배포까지

레포 하나가 서비스로 뜨기까지

코더가 레포를 등록하고 규격을 스스로 점검하면, 운영 관리자가 승인·배포한다. 배포는 소스 수집 → 빌드 → 기동 → 라우트 등록 → 헬스 대기를 거쳐 서브도메인으로 공개된다. 아래 파이프라인의 이동 점이 한 번의 배포가 흐르는 순서다.

배포 파이프라인 흐름 이동 점 = 한 번의 배포가 지나가는 순서 실서버(real)는 Kaniko 빌드+K8s apply, 로컬(docker)은 docker build+run
헬스(/healthz)가 응답할 때까지 기다린 뒤 "실행 중"으로 표시하므로, 상세 페이지의 "웹에서 바로 사용" 버튼은 준비가 끝나면 자동으로 서브도메인 링크로 바뀐다.
06 · 흐름 ③ 요청 처리

두 갈래의 요청 경로

사용자의 요청은 두 갈래다. 플랫폼 UI/API는 프론트를 거쳐 backend(JWT 검증)로, 배포된 서비스는 서브도메인으로 Traefik을 거쳐 해당 컨테이너로 간다.

플랫폼 경로 배포 서비스 경로(서브도메인)
실서버에서는 두 경로 모두 ingress-nginx(TLS·rate-limit·WAF) 뒤에 놓이고, 개별 서비스는 Ingress 서브도메인으로 노출된다(§11).
07 · 인프라 상세 · 격리

실서버 격리 — 신뢰 등급별 네임스페이스

여기서부터는 실서버(Kubernetes) 인프라 이야기다. 업로더 신뢰도에 따라 배포 위치와 격리 강도를 자동으로 다르게 적용한다(fail-closed).

내부 직원 · 반신뢰

CODER / ADMIN
  • 배포 위치 edu-services 네임스페이스
  • PodSecurity baseline 강제
  • 업무 특성상 사설망 접근 허용

불특정 다수 · 비신뢰

USER / 익명 / 불명
  • 배포 위치 edu-services-public
  • PodSecurity restricted 강제
  • 사설망 egress 차단 · (선택) gVisor 샌드박스
네임스페이스는 업로더 신뢰도로 자동 결정되며, 애매하면 무조건 비신뢰(더 안전한 쪽)로 붙인다.
08 · 인프라 상세 · 배포

GitHub 레포 → 실행 서비스 (real 모드)

실서버에서는 docker.sock을 쓰지 않고 Kaniko로 인클러스터 빌드해 레지스트리에 올린 뒤, 매니페스트를 렌더링해 신뢰등급 네임스페이스에 적용한다.

수집·검증 빌드·레지스트리 적용·공개
로컬(docker 모드)은 같은 앞단(수집·검증)을 쓰되 호스트 Docker로 docker build/run하고 Traefik 라우트 파일을 기록해 <slug>.localhost로 연다. real 모드는 위처럼 K8s로 배포한다.
09 · 인프라 상세 · 보안 격리

멀티테넌트 하드닝

여러 사람이 올린 서비스가 한 클러스터에 공존하므로, 네임스페이스마다 강한 격리 통제를 건다.

통제내용
PodSecurity Admission신뢰등급별 baseline/restricted 강제(비루트·캡드롭·seccomp)
ResourceQuota / LimitRange네임스페이스별 자원 상한 — 한 서비스가 자원을 독점하지 못하게
NetworkPolicydefault-deny + DNS 허용 + tier별 egress(공개 tier는 사설망 차단)
RuntimeClass(gVisor)비신뢰 서비스는 샌드박스 런타임으로 커널 격리(선택)
Kaniko 빌드docker.sock을 마운트하지 않는 안전 빌드. 미신뢰 입력은 정규식 검증 후 사용
CNI는 NetworkPolicy를 강제하는 Calico를 쓴다. 검증: 공개 tier의 사설망 egress 차단 / 내부 tier 허용을 대조 확인.
10 · 인프라 상세 · 운영

관측성과 오토스케일

지표·로그·트레이스 3축을 한 곳(Grafana)에서 상관 조회하고, 부하와 유휴에 맞춰 자동으로 늘리고 0까지 줄인다.

지표

Prometheus

kube-prometheus-stack. ServiceMonitor로 backend·서비스를 스크레이프, Alertmanager로 알림(BackendDown/CrashLoop 등).

로그

Loki + Promtail

LogQL로 조회, Grafana 연동.

트레이스

Tempo (OTLP)

트레이스↔로그 상관.

스케일

HPA + PDB

CPU 타깃으로 replica 증감, 최소가용 보장(무중단 롤링).

유휴 비용

KEDA scale-to-zero

요청 없으면 0으로, 요청 오면 0→1 콜드스타트.

DB 가용성

CloudNativePG

Postgres 클러스터 자동 장애조치(primary 승격).

11 · 인프라 상세 · 엣지

엣지 보안과 이미지 배급

클러스터 입구에서 TLS·속도제한·웹방화벽을 적용하고, 인증서는 자동 발급한다. 빌드한 이미지는 로컬 레지스트리로 노드가 당겨온다.

12 · 실행 환경

로컬(docker-compose) vs 실서버(K8s)

같은 코드가 두 환경에서 돈다. 로컬은 개발·시연용으로 가볍게, 실서버는 격리·확장·관측을 갖춰 운영한다.

항목로컬 (docker-compose · docker 모드)실서버 (Kubernetes · real 모드)
플랫폼backend :8088 · frontend Vite :5173backend(2 replica) · frontend(nginx) · ingress
인증auth-service :8089 · auth-db(:5433)deploy/k8s/auth/ (auth-service·auth-db·edu-auth-jwt Secret)
DBpostgres(:5432) · auth-db(:5433)CloudNativePG 클러스터(자동 장애조치)
배포 결과edu-svc-<slug> 컨테이너서비스 Pod+Service+Ingress(신뢰등급 ns)
라우팅Traefik :80 → <slug>.localhost(파일 프로바이더)ingress-nginx → <slug> 서브도메인(+WAF·TLS)
빌드호스트 Docker build/runKaniko 인클러스터 빌드 → registry
시크릿deploy/.env (EDU_JWT_SECRET 등)edu-auth-jwt 등 K8s Secret
두 환경 모두 EDU_JWT_SECRET을 auth-service(발급)와 backend(검증)가 공유한다. 로컬은 deploy/.env, 실서버는 Secret 한 곳에서 관리한다.

15 · 마무리

한 문장으로

"직원이 올린 프로그램을, 신뢰도에 맞춰 안전하게 빌드·격리 배포하고, 로그인한 사람이 역할에 맞는 권한으로 웹에서 바로 쓰게 하는 시스템."

인증(auth-service)·플랫폼(backend)·라우팅(Traefik)·실행(Kubernetes)이 관심사별로 분리되어 있어, SSO 추가·서비스 증가·환경 이전(로컬↔실서버) 어느 방향으로 커져도 변경 범위가 한 곳에 갇힌다.

인증은 auth-service로 분리
토큰은 각 서비스가 자체 검증
접속은 서브도메인
격리·확장·관측은 K8s
